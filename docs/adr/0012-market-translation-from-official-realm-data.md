# Market Translation renders the international Trade site in Chinese from official realm data

We add **Market Translation (市集漢化)**: on the international English Trade site (`www.pathofexile.com/trade` and `/trade2`, PoE 1 and PoE 2) the official page's own interface, dropdowns, filters and result rows are shown in Traditional or Simplified Chinese, each using the wording of its own official realm (Taiwan `pathofexile.tw`, China `poe.game.qq.com`). It is a global on/off Preference (`marketTranslation`, default off) whose target language is the resolved Display Locale (ADR-0011); it is active only when that resolves to `zh-TW` or `zh-CN`, and it never runs on the Taiwan, China or other localized realms, whose pages are already localized. Every translation is **display-only**: values the official site sends back to the Trade API (`type`, `name`, stat `id`, option `id`) are never changed, so searches, search IDs, Bookmarks and LiveSearch stay byte-identical to an untranslated page.

The official front end (verified on 2026-11-12, Vue 3 bundle `trade.*.js`) gives us four injection points, and each layer uses the most authoritative official source:

| Layer                 | Official mechanism                                                                                                           | Source of Chinese text                                                                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Interface strings     | Every label goes through `translate(key)`, which reads the global `__` dictionary; the international site never defines `__` | The realms' own public dictionaries `webtw.poecdn.com/js/translate.zh_TW.js` and `poecdn.game.qq.com/js/translate.zh_CN.js` (≈1,850 keys each; they cover 138 of the 149 keys the international bundle uses) |
| Dropdowns and filters | `/api/trade{,2}/data/{items,stats,static,filters}` are fetched on every page load (lscache no longer holds them)             | The same endpoints on the Taiwan and China realms, joined by stable `id`; items, which have no id, are joined by English name through the poexd-data item shards (ADR-0011)                                  |
| Result rows           | Each mod line carries `data-field="stat.<category>.stat_<hash>"`                                                             | The realm stat text for that id, with values taken from the English line through the matching English template                                                                                               |
| Our own UI            | Already localized by Display Locale (ADR-0011)                                                                               | Unchanged                                                                                                                                                                                                    |

Translation data is generated at build time by our update scripts from those official endpoints and files, never typed by hand, and shipped inside the extension package, lazy-loaded only when Market Translation is active. The dictionaries are parsed as data with a strict `__['…'] = '…';` pattern and never evaluated.

## Considered Options

- **Hand-written interface dictionary (poe-market-zh's approach)**: rejected; both official realms publish their own dictionaries, which match what players see in-game and on their realm's site, and we would otherwise have to maintain about 150 strings ourselves and choose between Taiwan and China wording by hand.
- **Fetch the Taiwan and US APIs at runtime in the background and join them (poe-market-zh)**: rejected; it needs the Taiwan realm to be reachable from every user's network, slows the first page load, and duplicates the joining work our update scripts already do once per release.
- **Serve the translation shards from the poexd-data jsDelivr CDN**: rejected for now; it requires a new `host_permissions` entry, which makes Chrome disable the extension on update until the user re-approves it, and a remote data dependency that the privacy policy does not yet cover. The shards are a few MB uncompressed for both games and both languages, which is acceptable in the package when they are lazy-loaded.
- **Rewrite the `/fetch` result JSON instead of the result DOM**: rejected; the official "copy item" text, PoB export and our own result features (price comparison, tier badges, mod highlighting) all read the English item JSON, and translating it would break them. Result rows are translated in the DOM by changing existing text nodes only.
- **Match result lines by full English text**: rejected as the primary key; `data-field` gives the exact stat id, and full-text matching stays only as a fallback for lines without it.
- **Translate by converting Traditional to Simplified characters**: rejected; the realms use different terms (for example Orb of Annulment is 撤銷石 in Taiwan and 剥离石 in China), so `zh-CN` text always comes from China realm data and falls back to English, never to converted Taiwan text.
- **A separate Market Translation language setting**: rejected; it would contradict ADR-0011's single Display Locale. Only the on/off switch and the bilingual option are new.

## Consequences

- The fetch wrapper for the four data endpoints must be installed before the official bundle's first fetch, which is earlier than today's injected `interceptor.js` can guarantee. Market Translation therefore needs a manifest-declared MAIN-world content script at `document_start` that only wraps those requests and holds their responses until the translation payload arrives from the isolated world (with a timeout, after which the English response passes through). It also defines `__` before the Vue app mounts. It must share one `fetch` wrapper chain with `network-observer.ts` so that our own features always receive the original English data.
- The dropdown label is the `text` field. In bilingual mode (`marketTranslationBilingual`, default on) it becomes `中文 English`, so typing English in the official dropdown still matches.
- Lines whose English form is a sign variant of the canonical template (such as `reduced` instead of `increased`) stay in English until poexd-data also emits every stat-description variant as an English/Chinese template pair; that data work is part of this feature.
- Features that read official DOM text, rather than ids or the Vuex store, must be checked against a translated page (`result-item-normalizer`, `result-price-presenter`, `result-mod-highlighter`, `hotkeys`, `poe-runtime-mutation`). The Page Locale used for typed fallback queries (ADR-0011) remains English on the international site even while the page is shown in Chinese.
- Untranslatable or unmatched entries keep their English text. A wrong translation is worse than an English one.
- Official site coupling points (the `__` hook, the four data endpoints, `data-field`, and the result row selectors) are listed in the implementation plan and checked by e2e. When one breaks, that layer silently falls back to English without affecting the others.
